# 危险判断逻辑优化与 CARLA 测试报告模块

本次项目围绕自动驾驶视觉辅助系统中的危险判断逻辑展开，将原先比较简单的目标框宽度阈值判断，扩展为融合车道关系、目标位置、目标类别、连续帧变化趋势和近似 TTC 的综合风险评估流程，并新增 CARLA 图像序列输入与测试报告导出能力。

![系统流程](assets/architecture_flow.png)

## 1. 项目背景

自动驾驶视觉辅助系统通常需要同时完成车道线识别、目标检测、危险等级判断和运行结果展示。原系统已经具备基础的车道线检测、YOLO 目标检测、仪表盘显示和危险事件截图功能，可以对道路前方车辆、行人等目标进行可视化标注。

但是在实际的自动驾驶场景中，“目标框变大”并不一定等于真正危险，“目标框暂时不大”也不一定代表安全。例如，位于画面边缘的大车可能并不在本车道内，直接用宽度阈值会造成误报；而正前方车辆在连续帧中快速接近时，即使当前目标框还没有达到宽度阈值，也已经具备潜在碰撞风险。

因此，本项目的核心目标不是简单增加一个页面，而是把危险判断从“单条件触发”升级为“多因素综合评估”，并把 CARLA 仿真环境导出的连续图像序列纳入测试流程，使项目能够更好地满足仿真数据验证、运行效果展示和工程可复现性的要求。

从工程验证的角度看，这类项目的重点不只是让程序在一段视频上显示检测框，而是要说明系统为什么这样判断、判断依据来自哪里、结果能否被复查。自动驾驶危险判断属于典型的多因素问题，单独依赖某个阈值虽然容易实现，但很难解释复杂场景中的风险变化。本次项目正是从这个问题出发，把视觉检测结果进一步转化为可解释的风险指标。

另外，CARLA 仿真器能够提供比较稳定的自动驾驶测试环境。相比随手找一段道路视频，CARLA 导出的图像序列具有明确的数据来源和连续帧关系，适合用来验证目标接近、车道重叠和 TTC 变化。因此，本项目把 CARLA 数据接入作为工程链路中的重要一环，而不是只把它当作普通图片来展示。

## 2. 原有问题

原来的危险判断主要依赖 `width_ratio > WARNING_RATIO`。这种方式实现简单，但存在明显局限。

- 只关注目标框宽度，没有判断目标是否处于本车道区域。
- 只利用当前帧信息，没有利用连续帧中目标尺度变化趋势。
- 无法区分普通提示、预警和危险制动等不同风险等级。
- 对 CARLA 连续帧测试结果缺少统一归档，不利于运行复查和代码维护。
- 没有逐帧 CSV 指标，后续很难分析风险变化过程。

![风险评分对比](assets/risk_score_comparison.png)

更具体地说，固定宽度阈值容易把“看起来大”的目标都归为危险，但自动驾驶系统真正关心的是目标是否会影响本车未来几秒内的行驶路径。例如，同样大小的目标框，如果一个目标位于本车道中心，另一个目标位于相邻车道边缘，它们的风险显然不应该相同。原逻辑没有车道区域约束，因此难以处理这种差异。

另一个问题是缺少时间维度。危险不是一个静止概念，而是随时间变化的过程。目标如果在连续帧中快速放大，说明它与本车的相对距离正在减小；目标如果逐渐偏离本车道，即使当前框较大，风险也可能下降。原逻辑只看当前帧，不能表达这种动态变化。

## 3. 改进目标

本次优化希望系统不仅能“看见目标”，还要能解释“为什么这个目标危险”。因此项目将改进目标拆分为四个层面。

第一是感知层。系统继续使用车道线检测和 YOLO 目标检测作为基础输入，保留原有可视化能力，保证改进不会破坏原有功能。

第二是风险层。新增 `RiskAssessor` 风险评估逻辑，把目标框面积、宽度、中心位置、车道区域重叠、底部位置、类别权重、面积增长趋势和 TTC 估计统一为 `risk_score`。

第三是数据层。新增 CARLA `sensor.camera.rgb` 图像序列输入支持，通过 `--input-kind images` 读取仿真平台导出的连续帧，使测试数据来源更符合自动驾驶仿真验证场景。

第四是报告层。新增 `CarlaTestReporter`，将运行结果输出为标注视频、关键截图、危险事件截图和逐帧 CSV 报告，方便对运行过程进行复查，也方便在项目说明中展示关键结果。

四个层面的设计让项目形成了比较完整的工程闭环：输入端来自 CARLA 或视频，处理中间有车道检测、目标检测和风险评分，输出端有可视化结果和指标文件。这样进行项目说明时可以从“为什么要改”讲到“怎么改”，再讲到“改完之后如何验证”，内容会比单纯介绍一个函数更完整。

在实现思路上，本项目尽量保留原系统的已有功能，把新增逻辑放在风险评估和报告导出部分。这样做的好处是改动范围比较清晰，不会把车道检测、目标检测、可视化展示全部推倒重写，也更符合在已有工程基础上做增量优化的要求。

## 4. 模块结构

本项目不是单独写一个孤立脚本，而是在原有自动驾驶视觉系统中补充风险评估和报告导出链路。整体结构可以理解为五个模块协同工作。

- `LaneSystem`：负责 HLS 颜色过滤、ROI 区域提取、Canny 边缘检测、霍夫线检测、车道线平滑和本车道区域生成。
- `YOLO Detector`：负责识别前方车辆、行人等交通目标，并输出检测框、类别和置信度。
- `RiskAssessor`：负责维护目标轨迹、计算综合风险分数、估计近似 TTC，并输出 `SAFE`、`WARNING`、`DANGER` 等风险等级。
- `FrameSource`：统一普通视频输入与 CARLA 图像序列输入，使同一套处理逻辑可以用于不同数据来源。
- `CarlaTestReporter`：负责保存标注视频、运行截图、危险事件截图和逐帧 CSV 报告。

![风险因素雷达图](assets/risk_factor_radar.png)

模块拆分后的优点是职责更加清楚。车道模块只关心道路结构，目标检测模块只关心交通参与者，风险评估模块负责把前两者的信息综合起来，报告模块负责把结果保存成文件。这样的结构便于后续继续扩展，例如把 YOLO 模型换成更高版本，或者把 TTC 估计替换为更精确的深度估计方法。

同时，`FrameSource` 的存在让输入来源更加统一。无论输入是普通视频文件，还是 CARLA 导出的连续图片目录，后续处理模块都可以按照“逐帧读取、逐帧分析、逐帧输出”的方式工作。这降低了不同数据源之间的耦合，也让项目更容易展示和复现。

## 5. 核心算法

本次优化的核心是 `RiskAssessor`。它不再只使用一个阈值判断危险，而是为每个目标计算综合风险分数。

风险分数主要由以下信息共同决定：目标框面积越大，说明目标越接近；目标框越靠近画面中心，越可能位于本车前方；目标与车道区域重叠越高，说明它越可能影响本车行驶；目标底部越靠近画面下方，通常表示距离更近；不同类别目标设置不同权重，例如车辆、行人和骑行者的风险优先级不同。

更重要的是，系统引入了连续帧趋势。项目通过 IoU 匹配将相邻帧中的同一目标关联起来，为目标维护 `track_id`，再根据目标框面积随时间的增长估计近似 TTC。如果一个目标在连续帧中快速变大，系统会认为它正在接近本车，风险等级会随之升高。

![TTC 时序](assets/ttc_timeline.png)

IoU 匹配的作用是让系统知道“当前帧的这个目标”和“上一帧的那个目标”是否属于同一个物体。只有建立了这种连续关系，系统才能计算面积增长趋势和近似 TTC。虽然这种方法没有使用真实深度传感器，但在单目图像场景下，它可以作为一种轻量级的接近趋势估计。

风险评分并不是为了替代目标检测，而是对目标检测结果进行二次解释。YOLO 告诉系统画面中有什么目标，`RiskAssessor` 则进一步判断这些目标与本车行驶风险之间的关系。这个分层逻辑也符合自动驾驶系统中“感知结果”和“决策依据”分离的设计思想。

## 6. CARLA 数据支持

仿真测试强调使用可复现的数据来源，因此本项目将 CARLA 图像序列作为重要输入来源。CARLA 中的 `sensor.camera.rgb` 可以导出连续前视图像帧，这些帧比单张测试图片更适合验证自动驾驶视觉系统，因为它们包含时间变化关系。

新增输入方式后，程序可以按照目录顺序读取 CARLA 导出的图片帧，并逐帧执行车道检测、目标检测、风险评分和报告保存。这样既保留了视频文件输入，也能直接处理仿真环境导出的图像序列。

典型运行方式如下：

```bash
python main.py path/to/carla_rgb_frames --input-kind images --output-dir output --no-display
```

运行后，系统会在 `output/` 目录下保存本次测试的完整结果。复查时既可以查看代码实现，也可以查看运行结果截图、视频和 CSV 指标。

CARLA 数据支持的意义在于，它让项目具备了可重复实验条件。同一组图像帧可以反复输入系统，用于比较不同风险阈值、不同评分权重和不同目标检测结果下的输出差异。如果后续继续优化算法，也可以直接复用这组数据作为基准测试集。

此外，CARLA 场景可以模拟普通道路视频中不容易收集到的情况，例如前车突然减速、行人横穿、车辆从侧方切入等。虽然本次项目主要处理 RGB 图像序列，但这个接口为后续接入更多 CARLA 传感器数据留下了空间。

## 7. 动态风险变化

下面的动图展示了本项目最关键的逻辑：同一个目标在连续帧中逐渐接近本车时，系统不再等到目标框超过固定阈值才报警，而是根据风险分数和 TTC 趋势逐步从 `SAFE` 进入 `WARNING`，最后进入 `DANGER`。

![连续帧风险变化](assets/risk_assessment_sequence.gif)

这种方式比单帧阈值更符合真实驾驶逻辑。驾驶员判断危险时，也不会只看物体当前大小，而会观察它是否在快速接近、是否位于本车道、是否处在车辆正前方。本项目就是把这种判断过程工程化到代码中。

在项目展示时，这一部分可以作为重点内容。动图能够直观说明系统不是突然报警，而是随着风险因素变化逐步提高危险等级。通过这一部分，也能更容易理解本项目和简单目标检测演示之间的区别。

## 8. 运行效果

优化后的系统运行界面会同时显示车道线、本车道区域、目标检测框、目标 ID、风险等级、风险分数和 TTC 信息。不同风险等级使用不同颜色显示：绿色表示安全，黄色表示预警，红色表示危险。

当目标进入本车道区域，并且面积持续增大或 TTC 过小时，系统会进入 `DANGER` 状态，在画面中显示 `BRAKE!`，同时触发危险事件截图。底部仪表盘会展示 FPS、偏移指示、虚拟方向盘、`RISK`、`TTC` 和当前系统状态，使运行过程更加直观。

![运行界面](assets/runtime_dashboard_mock.png)

运行界面中的信息不是单纯为了美观，而是为了让风险判断过程可解释。目标框旁边显示风险等级和目标 ID，可以帮助观察同一目标在不同帧中的变化；仪表盘显示 TTC 和 RISK，可以把算法内部计算结果直接暴露出来，方便调试和展示。

如果只输出最终的 `BRAKE!`，使用者很难知道系统为什么触发制动。现在页面中展示了风险分数、TTC 和车道关系，能够说明危险判断是由多个因素共同决定的，这会让项目说明更有说服力。

## 9. 报告输出

为了让项目更方便归档和复查，本次新增 `CarlaTestReporter`。它的作用是把一次测试运行自动整理成可以复查的结果文件，而不是只在屏幕上短暂显示。

输出内容包括带标注的视频文件、关键帧截图、危险事件截图和逐帧 CSV 报告。CSV 报告可以记录帧号、目标数量、最大风险分数、最小 TTC、当前状态等信息。这样一来，展示时可以呈现图像效果，复查时可以检查数据记录，后续如果继续优化算法，也可以用同一批 CARLA 帧进行对比。

![报告输出结构](assets/report_artifacts_overview.png)

报告输出模块解决的是“运行结果如何保存”的问题。很多演示程序只能在窗口中看一遍效果，程序关闭后就很难复查。本项目把运行结果保存为多个文件，使得一次实验可以被反复查看，也能在 PR 说明、技术报告和项目展示中复用。

CSV 文件尤其适合做后续分析。比如可以统计危险帧数量、平均风险分数、最小 TTC 出现在哪一帧、不同目标类别触发预警的比例等。这些数据虽然不是最终控制指令，但可以作为评价危险判断逻辑是否合理的重要依据。

## 10. 测试与验证

本项目的验证重点不是单纯让程序启动，而是检查输入、处理、输出三部分是否形成闭环。

在输入方面，系统需要能够读取普通视频，也需要能够读取 CARLA 连续图像帧目录。在处理方面，系统需要完成车道检测、目标检测、目标跟踪、TTC 估计和风险等级输出。在输出方面，系统需要保存标注结果、关键截图、危险事件截图和 CSV 报告。

相较于原始版本，本次修改使测试过程更加清楚：一组 CARLA 仿真帧进入系统后，会得到一组可复现的运行结果，既能看视觉效果，也能看逐帧指标。这一点对工程复现非常重要，因为项目不仅要说明“改了什么”，还要能展示“改完之后怎么运行、运行结果在哪里”。

测试验证可以从三个角度展开。第一是功能验证，确认程序能够读取图像帧并生成输出文件；第二是逻辑验证，确认目标接近时风险等级会升高，目标远离或偏离车道时风险降低；第三是结果验证，确认导出的视频、截图和 CSV 与运行过程一致。

如果需要进行完整展示，可以把测试过程讲成一条流水线：CARLA 生成图像帧，程序逐帧读取，车道和目标检测模块提取关键信息，风险模块计算评分，报告模块保存结果。这样可以清楚呈现项目从输入到输出的完整路径。

## 11. 工程量说明

本项目的工程量主要体现在以下几个方面。

- 新增综合风险评估逻辑，从单一宽度阈值扩展为多因素评分。
- 新增目标连续帧关联，为每个目标维护轨迹 ID。
- 新增基于目标框面积变化的近似 TTC 估计。
- 新增 CARLA 图像序列输入，支持仿真器导出的连续帧测试。
- 新增测试报告导出模块，保存视频、截图、危险事件和 CSV 指标。
- 优化运行展示信息，使画面能够显示风险等级、风险分数和 TTC。
- 形成从仿真数据输入到运行结果归档的完整闭环。

这些改进不是简单增加几行说明文字，而是围绕自动驾驶视觉辅助系统的危险判断和测试验证流程做了一次比较完整的工程化增强。

从代码组织上看，本次项目包含输入适配、算法计算、结果展示、文件输出和文档说明多个部分。它不是只修改一个变量或增加一个小函数，而是围绕一个明确的自动驾驶问题，对原系统的判断逻辑和验证流程进行组合式增强。

从仿真验证角度看，本项目使用了 CARLA 仿真器数据，具备运行效果图、动态变化展示和可复查的输出结果。相比仅提供代码，配套文档和页面能够更完整地说明项目价值，也便于理解整体工程量。

## 12. 项目创新点

本项目的创新点可以概括为三个方面。

第一，危险判断从“是否超过宽度阈值”升级为“综合风险评分”。这种方式能够结合空间位置和目标类别，减少边缘目标误报，也能更早发现正前方接近目标。

第二，系统加入了连续帧趋势分析。通过目标轨迹和面积增长估计 TTC，项目能够利用 CARLA 连续帧中的时间信息，而不是只把每一帧当作孤立图片处理。

第三，项目增加了报告导出机制。`CarlaTestReporter` 让运行结果从临时展示变成可保存、可复现、可复查的文件，这对项目归档和后续实验对比都更有价值。

除此之外，本项目还强调“可解释性”。危险判断不再是黑盒式地给出一个状态，而是可以通过风险分数、TTC、车道重叠和目标轨迹来解释。对于自动驾驶辅助系统而言，可解释性非常重要，因为系统报警时必须能够说明报警依据。

本项目也具有一定扩展空间。后续可以继续接入 CARLA 的深度相机、语义分割相机或雷达数据，把现在的近似 TTC 改成更精确的距离估计；也可以把风险评分结果进一步连接到车辆控制模块，用于模拟减速或制动策略。

## 13. 总结

本次项目围绕自动驾驶视觉辅助系统中的危险判断逻辑进行了系统性优化。改进后的系统不仅能检测车道和目标，还能根据目标与车道的关系、目标在画面中的位置、目标类别、连续帧变化趋势和近似 TTC 计算综合风险，并将结果以视频、截图和 CSV 报告形式保存下来。

从技术说明角度看，这个项目具备明确的问题来源、清晰的改进目标、完整的算法流程、可展示的运行效果和可复查的输出文件。从工程实现角度看，它把感知、风险评估、仿真输入和测试报告拆分得更加清楚，为后续继续接入更多 CARLA 场景、更多目标类别和更精细的控制策略提供了基础。
